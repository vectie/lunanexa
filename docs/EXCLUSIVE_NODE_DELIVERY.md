# 整机独占、容器交付与模型缓存方案

日期：2026-09-23

状态：用户已确认的产品方向与实施要求；不是现有功能全部完成的声明。
本文来自侧边架构讨论，供主任务实施和验收使用。本次仅新增文档，不改变
线上权限、调度、缓存、租约或已有交付入口。

## 1. 核心决策

业务的最小资源分配单位是 **一整台 DGX Spark**，允许订单占用多台。
同一租期内，所分配节点不与其他客户或平台推理任务混用。

默认 IaaS 采用 **独占节点上的 GPU 容器实例 + 用户持久盘 + 宿主机模型缓存**。
用户能自主使用环境和 GPU，但不直接管理宿主机。不必为此引入 GPU 虚拟机。

“整机资源独占”与“裸机管理权交付”是两个概念：前者不自动赋予宿主机 root、
驱动、内核、网络或容器运行时管理权限。产品名称、订单说明及 UI 不得混淆。

原有裸机租赁是否保留为特殊交付选项尚未单独决定；本文不授权删除或替换其入口。

## 2. 三种交付方式

| 方式 | 交付内容 | 用户管理边界 | 平台管理边界 |
| --- | --- | --- | --- |
| IaaS | 独占节点上的 GPU 容器实例、终端/SSH、持久盘、获准模型挂载 | 用户软件、依赖、程序、模型运行和自己的服务 | 宿主机、GPU 驱动、容器运行时、网络隔离、租约与回收 |
| MaaS | 独占资源上的受管模型端点、API 凭据与额度 | API 调用及允许的模型参数 | 模型准备、加载、推理服务、健康检查、计量与服务生命周期 |
| PaaS | 独占资源上的 WebIDE/ComfyUI 工作空间及所需模型服务 | 代码、项目、工作流、配置和生成结果 | 应用环境、持久化、模型连接、启动恢复与底层基础设施 |

分类依据是管理责任与交付契约，不是容器数量。一个交付可能包含应用、推理、
代理等多个容器；分布式推理也可能跨多台已分配节点。

对于 ComfyUI + MiniMax H3，典型形态是用户应用容器调用该客户授权范围内的受管
推理服务。不得为节约资源而静默复用另一个客户独占节点上的服务。

## 3. GPU 与整机调度

容器通过 NVIDIA 容器运行时使用实际 GPU，不是模拟 GPU，也不是 VM GPU 直通。
现有 Kubernetes/containerd 应继续承担运行时管理，不要求额外部署宿主 Docker。

调度要求：

1. 在启动任何用户工作负载前，原子预留订单所需的完整节点集合。
2. 独占约束同时覆盖租户任务、平台 MaaS/PaaS 任务与其他入口，不能只依赖某个
   Pod 的 GPU resource request。
3. 必要的监控、节点代理和基础设施服务可以保留，并明确预留其系统资源。
4. 已占用节点不可直接抢占；停止与排空必须有实际完成证据，再交给下一租户。
5. 同一客户可以让多个容器共享其分配节点的 GPU，但必须评估总内存、推理缓存、
   并发和带宽，不能因容器隔离而假设资源无限。
6. 多节点订单必须防止部分分配被误报为全部就绪；失败、重试与释放应可对账。

Spark 的 CPU 与 GPU 共享系统内存，不能把标称内存全部当成可分配给模型的显存。
磁盘上复用同一份权重也不代表多个推理进程自动共享运行时权重或 KV cache。

## 4. 三层存储

| 层 | 内容 | 权限与生命周期 |
| --- | --- | --- |
| 数据节点模型源 | 经准入的模型文件、版本清单、摘要及来源记录 | 平台管理，作为计算节点补齐模型的来源 |
| 计算节点公共模型缓存 | 按不可变版本/摘要组织的已验证模型 | 平台写入，获准工作负载只读挂载，跨租期复用 |
| 用户持久盘 | 代码、工作流、配置、输入输出、私有模型和微调产物 | 租户隔离可读写，与容器生命周期解耦 |

容器中的 `/workspace` 等工作目录挂载持久卷；不能只依赖容器可写层保存数据。
用户停止、重建容器后，应能重新打开原工作。跨节点恢复需要对应存储能力或迁移，
不能把本地 PVC 描述成天然具备高可用。

模型挂载由平台根据已验证的身份、订单、许可和版本生成；用户不能自由指定宿主机
目录。不得开放宿主 Docker/containerd socket、任意 hostPath、宿主网络或特权模式。

只读必须在实际挂载层落实，不仅是 UI 标记。只读可防止修改共享模型，但不能防止
获得读取权限的用户复制权重；不允许向用户交付权重的模型，只能通过 API 使用。
用户私有模型不得未经同意提升为跨租户公共缓存。

## 5. 模型准备与缓存命中链路

```text
用户选择服务、模型和规格
  → 校验身份、许可、租约与资源权限
  → 从可分配节点中优先选择已有目标模型缓存的节点
  → 预留完整节点集合
  → 同一客户授权范围内的匹配服务已运行？
      是：检查版本、健康与授权后复用
      否：目标节点有完整有效的指定版本缓存？
          是：直接使用本地缓存
          否：从 data node 下载/断点续传 → 校验 → 原子发布缓存
  → 只读挂载模型并启动推理服务
  → 实际健康检查与模型响应验证
  → 启动/连接应用工作区
  → 用户可以使用
```

约束：

- 缓存键使用不可变版本或内容摘要，不能仅凭模型名称相同就认定命中。
- 不应每次开机都全量下载，也不应在每轮对账中重复哈希全部大型权重。
- 首次下载完整性校验、后续复用检查、损坏修复需形成明确策略；快速检查不能被
  宣传为每次都完成了逐字节完整性验证。
- 同一模型并发下载应协调，半成品不对运行实例可见；失败可恢复，不误报就绪。
- 有效缓存优先，但不能为了命中缓存违反租户隔离、整机独占或资源容量约束。
- 模型来自 data node 不等于必须使用某个固定协议；实际对象存储/HTTP适配与
  断点续传能力需按部署验证，不用路径或 URI 名称冒充实际传输证据。

## 6. 回收与缓存保留

租约到期或用户停止服务时，分别处理：

1. 撤销访问与凭据，停止用户进程和工作负载，确认 GPU/节点已释放。
2. 用户数据按已展示的保留、导出和删除策略处理；不能因删容器而意外丢失。
3. 公共模型缓存继续保留，不随租约或单个部署结束自动删除。
4. 缓存根据磁盘高低水位、闲置时长、固定保留项及引用关系回收；运行中引用的
   缓存不可删除，清理不能误触用户持久盘。
5. 下一租户只能获得自己的数据和获准公共模型，不能看到前一租户残留。

删除用户文件不等于已经完成磁盘级安全擦除；如交付承诺要求更强清理，必须单独
定义机制和验证证据。

## 7. 公网入口

公网入口使用如下链路：

```text
用户浏览器
  → 公网 IP/端口
  → 管理员在外部网关配置 NAT
  → 192.168.2.175:已公布的服务端口
  → 平台认证与工作区路由网关
  → 当前用户获准的工作区
```

平台负责部署并检查 `.175` 的监听与上游路由，并向管理员提供准确的 NAT 映射。
不把用户直接导向裸露的共享应用或 Kubernetes 内部地址，不再跳到用户本机
`127.0.0.1`。模型调用经平台配置的内部模型网关，不为每个模型另开公网端口。

外层 HTTP 验收配置不应被描述成生产安全完成；认证、租户隔离和内部可信通信仍
需保留，后续外部 TLS 切换应有明确配置边界。

## 8. 一键启动的定义与 UI 反馈

“启动 ComfyUI + MiniMax H3”包含模型与应用整条链，不能只打开空的 ComfyUI。
用户应看到：

- 资源预留中：节点数、可用性和等待原因。
- 模型准备中：本地命中/需要下载、版本、已传输量与可用的进度信息。
- 模型启动中：加载阶段、失败原因和可执行的重试。
- 工作区启动中：持久盘恢复、应用启动与模型连接。
- 可使用：应用可打开，正确模型可响应。

已有服务可跳过不必要步骤，但应显示“复用现有实例/本地缓存”，不能伪造执行记录。
发出部署请求、容器 Running、生成 handoff 或打开页面，都不足以证明完整就绪。
企业端与管理端必须对同一订单、租期、资源、模型版本和运行状态给出一致反馈。

## 9. 验收要求

以下各项均需真实证据，不以单元测试或清单勾选替代：

1. 新用户按授权流程获得独占节点，另一租户及平台任务不能占用该节点。
2. IaaS 容器可使用 CUDA/GPU、安装允许的软件，但不能控制宿主运行时或访问他人数据。
3. 本地模型缓存命中时不发生权重全量重传；缺失时从 data node 补齐，断线可恢复。
4. 同一模型版本只读挂载正确；错误版本、半成品和无许可模型不能进入实例。
5. MaaS 实际调用成功，计量归属正确；PaaS 能通过正确模型完成一次真实生成。
6. ComfyUI 生成结果可查看和下载；工作流/代码保存后，关闭、重开以及容器重建后仍在。
7. 到期后访问和任务被回收，持久数据及公共缓存按各自策略保留，节点可安全再分配。
8. 两侧 UI 每一步有明确反馈，公网启动不跳本机或内网地址，失败和重试不造成重复分配。
9. 多节点订单、并发启动、部分失败、控制器重启及缓存空间不足的行为可恢复、可对账。

主任务继续以公网 UI 完成业务操作；源代码修复、自动化测试与部署按主任务已有范围
执行。本文不是延长过期测试权限、扩大授权或跳过安全门的凭据。

## 10. 已观察到的实现基础与缺口

以下为侧讨论在 2026-09-22 的只读观察，实施前必须重新核实：

- `node/artifact_materializer.mbt` 已有摘要寻址缓存、目录清单/尺寸复用检查、
  下载校验和 HTTP Range 续传逻辑。
- `cmd/node/main.mbt` 对账末尾调用 `prune_unassigned`，仅保留当前 assignment 和
  supervisor 引用；需检查并补齐停止部署后的闲置缓存保留策略。
- 已部署 H3 FL2VA 固定在 Spark 25e2，使用本地
  `/var/lib/lunanexa-models/minimaxh3/minimaxh3/FL2VA`。
- 已部署 H3 Ref2VA 固定在 Spark 3782，使用本地
  `/var/lib/lunanexa-models/minimaxh3/minimaxh3/Ref2VA`。
- 上述 H3 部署可复用本地目录，但固定 hostPath 本身不提供目录缺失时自动从
  data node 补齐的能力；须统一接入模型准备状态机。
- 当时企业端仍有旧的 MoonDesk 本机交接地址，不能据此宣称公网 PaaS 已交付。

## 11. 官方技术边界参考

- [DGX Spark 容器 GPU 支持](https://docs.nvidia.com/dgx/dgx-spark/nvidia-container-runtime-for-docker.html)：容器可使用真实 GPU。
- [DGX Spark 支持范围](https://docs.nvidia.com/dgx/dgx-spark/support.html)：官方不支持虚拟化 GPU 直通。
- [Spark 统一内存架构](https://docs.nvidia.com/dgx/dgx-spark-porting-guide/overview.html)：CPU/GPU 共享物理内存。
- [Kubernetes 持久卷](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)及[卷安全边界](https://kubernetes.io/docs/concepts/storage/volumes/)：持久化、节点约束和只读挂载需独立落实。

容器共享宿主内核，即使整机租期独占，也不得宣称提供了虚拟机级硬件隔离。
